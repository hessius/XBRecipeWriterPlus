# M5 Phase 3: The Rail — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One row of chrome above the library that can search it, sort it and narrow it, on a library that is already too long to scan.

**Architecture:** The list stops being "every recipe, sorted in JavaScript" and becomes the answer to a query. `library/libraryQuery.ts` builds one SQL statement against the index columns phase 1 added, joined to `brews` for the two axes that need evidence; `RecipeDatabase.queryRecipes` runs it and hydrates the blobs it names. Nothing new is stored: the query is assembled from three settings keys and the rail's own transient state. The filter vocabulary is derived from index counts rather than listed, which is what makes phase 4's shelf grid a second drawing of a thing that already exists rather than a second implementation of it.

**Tech Stack:** TypeScript, `expo-sqlite` (sync API), Tamagui, Jest with `@testing-library/react-native` v14, and the `node:sqlite` harness in `library/__tests__/`.

**Design docs:**
- `docs/superpowers/specs/2026-09-16-library-shelves-design.md` — §The rail, §Sort, §Favourites, §Storage
- `docs/superpowers/specs/2026-09-14-recipe-index-design.md` — the index this queries

**Branch:** `m5-rail`, off `main`, in its own worktree.

**Issue:** #72.

---

## Scope, and the two things cut from it

The design's phase 3 bullet lists four things: search, sort, filter chips, and
the view segmented pair. This plan ships three.

**The view segmented pair is deferred to phase 4, with `libraryView`.** The pair
switches between the list and the *shelf grid* (§"The grid is a picker for the
lens, not a second home"), and the shelf grid is phase 4. Shipping the switch
now would put a segment on screen whose other half does not exist, which is the
dead-field mistake the foundation plan refused for `description`. The rail is
built with the leading cluster as a list so the pair is an insertion rather than
a rework, and the divider that separates pinned controls from scrolling ones is
drawn from the start.

**The Rating axis is deferred to #99.** Every recipe would score identically
until a rating can be given, so the axis would sort nothing and the chip would
name a state the library is not in. The axis table in `librarySort.ts` is
written so adding it later is one entry.

**In scope:** search, five sort axes with direction and favourites-first, a
derived filter vocabulary with chips, the rail itself, and the section headers
favourites-first implies.

## Before you start

Read the design's §The rail, §Sort and §Favourites. This plan implements them
and does not repeat their reasoning.

Repository rules that bite here specifically:

- **Colour comes from `constants/colors.ts`**, timing and easing from
  `constants/motion.ts`. No hex literals and no bespoke durations in `app/` or
  `components/`.
- **The React Compiler is on.** No `useMemo`, no `useCallback`, and never read
  whole `props` inside a hook. State cannot be seeded or reset from an effect:
  store a reading together with what it came from and discard it at render when
  they no longer match (`hooks/useTraceAnimation.ts` is the worked example).
- **A setting is not backed up by being in `DEFAULTS`.** `app/settings.tsx`
  holds an explicit `settingsSnapshot()` allowlist and it has to be edited too.
  This is how `showHints` went missing.
- **Component tests await `render`, `fireEvent` and `renderHook`**, and use
  `renderWithProviders`. RNTL v14 has no `UNSAFE_getAllByType`: assert on text,
  test IDs and accessible labels.
- **One `render` per `it`.** Never call `unmount()`.
- **No em dashes in user-facing copy**, and dashes avoided generally. Doto caps
  for system labels, Inter sentence case for prose.
- Run `npm run typecheck`, `npm run lint` and `npm test` before each commit.
  `npx expo-doctor` is a hard CI gate; if it fails on a patch mismatch you did
  not cause, bump the pin in `package.json` by hand, because npm 12 refuses
  `npx expo install --fix` with `EALLOWSCRIPTS`.

### Task 1: The three settings keys

Add to `library/Settings.ts` `DEFAULTS`, each with the comment style already
used there (what it is for, not what it does):

| Key | Default |
|---|---|
| `librarySort` | `"name"` |
| `librarySortDirection` | `"asc"` |
| `libraryFavouritesFirst` | `false` |

Then add all three to `settingsSnapshot()` in `app/settings.tsx`. A test in
`library/__tests__/backup.test.ts` should assert that every key in `DEFAULTS`
appears in a built backup, if one does not already exist — that is the check
that makes this class of omission impossible rather than merely noticed.

`librarySort` and `librarySortDirection` are typed unions, not bare strings, so
an invalid stored value cannot reach the query builder.

**Verify:** `npm test -- Settings backup`.

---

### Task 2: The sort vocabulary

New `library/librarySort.ts`, pure TypeScript, no React, no SQL execution.

Exports one table and the functions that read it:

```ts
export type SortAxis = "name" | "added" | "lastBrewed" | "timesBrewed" | "ratio";
export type SortDirection = "asc" | "desc";
```

For each axis: its chip label (`ADDED`, `LAST BREWED`, ...), its two direction
labels from the design's table (`A TO Z` / `Z TO A`, `NEWEST` / `OLDEST`,
`RECENT` / `LONGEST AGO`, `MOST` / `LEAST`, `LOW TO HIGH` / `HIGH TO LOW`), its
default direction, and the ORDER BY fragment it contributes.

Three rules from the design are this module's invariants, and each gets a test:

- **A sort never hides a recipe.** A recipe never brewed sorts last under both
  brew axes, in *both* directions. Not "NULLs last" — deliberately last, so
  `LONGEST AGO` does not open with nine recipes nobody has ever brewed.
- **Every axis falls back to name for ties**, and name falls back to `uuid`, so
  two recipes with the same name do not swap places between launches.
- **The default is `name`/`asc`**, and `isDefaultSort()` answers whether the
  chip should name itself.

**Verify:** unit tests on the fragments and on `isDefaultSort`. No database.

### Task 3: The query builder

New `library/libraryQuery.ts`. One exported function that takes a query value
and returns `{sql, params}`. It executes nothing, which is what makes it
testable without a device.

```ts
export type LibraryQuery = {
    search: string;
    filters: string[];       // filter ids, ANDed
    sort: SortAxis;
    direction: SortDirection;
    favouritesFirst: boolean;
};
```

Shape of the statement:

- `SELECT uuid FROM recipes` with a `LEFT JOIN` on an aggregate subquery over
  `brews` grouped by `recipeUuid`, giving `lastBrewedAt` and `brewCount`. The
  join is always present, because a query that changes shape with its inputs is
  a query that is only tested in one shape.
- **Search** matches `sortName`, `sharedBy`, `xid` and the tag rows, case
  insensitively, as a substring. It does **not** match the placeholder name: it
  is a formatted date and searching "2026" should not return every unnamed
  recipe. `description` is matched too, even though nothing can author one yet,
  because the column exists and excluding it would be a rule to remember later.
  LIKE arguments are escaped: a recipe named `100%` must not match everything.
- **Filters** are ANDed, each contributing a fragment from Task 4.
- **ORDER BY** is, in order: the favourites-first modifier when on
  (`favourite DESC`), the axis fragment, then the name and uuid tie breaks.
- No `LIMIT`. A library of a hundred and eighty is not a paging problem, and a
  limit would be a silent partial answer.

Then `RecipeDatabase.queryRecipes(query): Recipe[]`, which runs it and hydrates
each uuid through the existing single-row read, preserving order.

**Test with the `node:sqlite` harness**, which the recipe index tests already
use: build a database of a dozen recipes with known names, dates, ratios and
brews, then assert the returned order for each axis and direction, for search,
for a filter, and for favourites-first composing with a non-default axis. Pin
the "never brewed sorts last in both directions" case explicitly.

**Verify:** `npx jest libraryQuery`.

### Task 4: The derived filter vocabulary

New `library/libraryFilters.ts`. Declares the stock filters as index queries,
exactly the list in the design's §Stock auto shelves, minus the author filters
which need a `SELECT DISTINCT sharedBy` and are derived at runtime.

Each filter: an id, a Doto caps label (`TEA`, `SINGLE POUR`, `GRINDER OFF`,
`STRONG`, ...), and a WHERE fragment.

The vocabulary offered to the user is **derived from counts, not listed**:

- A filter holding **fewer than 3** recipes is not offered.
- A filter holding **more than 80%** of the library is not offered.
- Both rules apply to derived filters only. Nothing a person authored is
  suppressed, which matters when tags become manual shelves in phase 4.

One `availableFilters(counts, librarySize)` function does that, and phase 4's
shelf grid calls the same one. Write it so it is obvious that it is the shared
mechanism: the grid and the chip row must never disagree about what exists.

**Verify:** unit tests on suppression at the boundaries — exactly 3 is offered,
exactly 80% is offered, 81% is not.

### Task 5: The rail

`components/RailChip.tsx` first, because everything in the rail is one:

- **44 pt tall, always**, and 44 wide when icon-only. `HomeHeader.tsx:19`
  explains why this cannot be rescued with `hitSlop` on adjacent controls.
- Inactive: the outline treatment. Active: the accent fill. The editor's action
  bar learned this the hard way this week — fill carries state, ink only agrees
  with it, and one step of grey is not a state.
- A chip that is active and has something to say names itself.

Then `components/LibraryRail.tsx`:

- A pinned leading cluster — search, sort — then a hairline divider, then a
  horizontally scrolling chip row. The divider is structural: it is how a user
  knows part of the row scrolls and part does not.
- The cluster is a list so that phase 4 can insert the view pair into it.
- The rail shrinks with scroll by losing its **own vertical padding only**.
  Chip height never moves. Timing from `constants/motion.ts`.

**Verify:** component tests on chip height under both the expanded and shrunk
rail, on the active fill, and on the divider being present.

### Task 6: The sort sheet

`components/SortSheet.tsx`, through `XbrwSheet` like every other sheet.

- The five axes as a list, the selected one marked.
- **Direction is a segmented pair, worded**, not arrowed, and its two words come
  from the axis: choosing an axis changes the words under it.
- **Favourites first is a switch beneath the direction**, not a sixth axis,
  because it composes with the sort rather than replacing it.
- Choosing an axis applies that axis's default direction, so a sort is never two
  taps when one would do.

**Verify:** component tests that the direction words follow the axis, that
choosing an axis writes both settings, and that the switch is independent of
both.

---

### Task 7: Search

The search chip expands into a field on tap and collapses on clear, per the
design: it is the most expensive control in width and the least used at this
library size.

- Expansion animates from `constants/motion.ts`; it honours `useReducedMotion`.
- The field is debounced before it reaches the query, at the same value
  `useRecipeImport` uses, so the two fields in the app feel the same.
- Clearing collapses it and drops the search term. Dismissing the keyboard does
  not, because a user who typed a term and looked at the results still has one.
- The chip is accented while a term is active, so a filtered library never looks
  like an unfiltered one.

**Verify:** component tests on expand, on clear-collapses, and on the accent
while a term is held.

### Task 8: Binding it to the library

New `hooks/useLibraryQuery.ts`, which owns the rail's transient state (search
term, active filters) and reads the three settings, and hands `useRecipeLibrary`
a query rather than nothing.

`useRecipeLibrary` stops sorting in JavaScript. Its `loadRecipes` helper becomes
`db.queryRecipes(query)`, and the `RecipeStore` interface it declares grows the
method. Every existing caller and mock in the tests has to grow it too; do not
leave `retrieveAllRecipes` behind as a second path to the same list, or the two
will disagree the first time someone edits one.

**Verify:** `npx jest useRecipeLibrary useLibraryQuery`.

---

### Task 9: The home screen

Wire the rail into `app/index.tsx`, under the collapsing header.

- **Section headers.** With favourites-first on, `FAVOURITES` and `ALL RECIPES`
  in Doto caps, drawn **only when both sections have something in them**. A
  heading over the whole list is not a heading.
- **An empty result is not an empty library.** The existing empty state invites
  a first import and would be wrong here. A search or filter that matches
  nothing says so, names the term or the filters, and offers to clear them.
- The rail is not drawn at all when the library is empty, for the same reason.

**Verify:** screen tests for the two-section case, the one-section case, the
no-results case and the empty-library case.

---

### Task 10: The sweep

- **Accessibility.** Every chip is a button with a label that names its state,
  not its glyph: "Sort by date added, newest first", not "Sort". The rail is
  reachable in order. A screen reader user has no horizontal scroll gesture, so
  confirm the chip row is traversable.
- **Copy.** No em dashes. Doto caps for the chips and headers, Inter for the
  no-results prose. `sharedBy` filters say "arrived from", never "by".
- **Hints.** If `showHints` is on, the rail earns one line the first time a
  library is large enough to need it. One, not four.
- **Docs.** Update the design's shipping order to mark phase 3 done and record
  the two deferrals. Update `.github/copilot-instructions.md` with the query
  layer, since "the library list is a SQL query now" is exactly the kind of
  thing a future contributor would otherwise rediscover by reading four files.

**Verify:** full gate — `npm run typecheck && npm run lint && npm test && npx
expo-doctor` — then a device pass on the smallest phone, because the rail's
whole argument is a width budget and RNTL performs no layout.

## What "done" looks like

A library of forty recipes where you can find the tea ones in one tap, the
neglected ones in two, and a recipe by name in three keystrokes, with the
favourites kept at the top if you asked for that. Nothing new stored, and phase
4 able to draw a grid of the same filters without deriving them a second time.
