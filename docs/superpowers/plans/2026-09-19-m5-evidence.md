# M5 phase 7: the evidence, the unwatched brew, and the shelf art

Status: in progress.

The audit that opened this phase found the shipping order in
[`2026-09-16-library-shelves-design.md`](../specs/2026-09-16-library-shelves-design.md)
marks items 1, 3, 4, 4b, 5 and 6 shipped and item **2 the row** not. What is
left of item 2 is the half that was blocked: **evidence**. Two further pieces of
the design were never built at all -- the **unobserved brew**, without which a
card-only user can never produce a rating and the axis #99 just added sorts
nothing for them, and the **shelf art**, which `ShelfMark` still stands in for
with a placeholder bar. #126 is the one remaining supply gap of #72 and #106.

So: four tasks and a gate, in dependency order. Evidence cannot be drawn before
there is something to draw, and a card-only user cannot produce that something
until task 1 lands.

## Task 1: A rating you type by hand

Spec §"Rating, and the brew nobody watched".

- [x] `library/brew/BrewRecord.ts`: a `watched?: boolean` field, absent meaning
      true. **An explicit field rather than inferring it from `waterTotal 0 and
      heldSeconds 0`**, which the spec offers as the shape of the row rather
      than as the test for one: a brew that failed at `notEnoughWater` before a
      drop was poured has both of those at zero too, and it is a brew the app
      watched closely enough to know why it stopped. Inferring would file it as
      something a person typed.
- [x] `library/BrewDatabase.ts`: a `watched` INTEGER column with the same
      `ALTER TABLE` migration shape as `rating`, `note` and `pinned`, defaulting
      to 1 so every existing row stays a watched brew.
- [x] `BrewDatabase.logUnobserved(recipe, rating)`: writes one row with no
      samples, `hasStream 0`, `watched 0`, `outcome` complete, `waterTotal 0`,
      `cupTotal 0`, `heldSeconds 0`, `pours 0`, and the recipe's name and accent
      snapshotted as every other insert does.
- [x] It is pinned on arrival. An unobserved brew is nothing **but** a
      judgement, so the sweep rule that protects a judged brew protects this one
      for the same reason, and it has no samples for the sweep to take anyway.
- [x] `summaryFor` keeps counting it: it is a brew. Any machine-derived figure
      must not. Audit every aggregate over `brews` for one that would now
      average a zero, and exclude on `watched = 1` where it would.
- [x] `library/backup.ts`: `watched` joins `OPTIONAL_BREW_FIELDS`, so a hand
      logged brew survives a new phone. `restore` keeps writing `hasStream 0`
      and must not flip `watched`.
- [x] Tests: an unobserved brew counts for times and last brewed; it is excluded
      from every water figure; it survives a backup round trip; a pre-migration
      row reads as watched.

## Task 2: One star, two meanings

The entry point, and the only thing the user touches.

- [x] A star in `HistorySection`, which is already named HOW IT HAS GONE,
      already in the ABOUT deck's order, and whose own comment says the rating
      summary lands there.
- [x] **One gesture, two outcomes.** If the recipe has a brew from today, the
      star rates that brew. If not, it writes an unobserved one. Never
      explained, because it never needs to be: in both cases the user said this
      coffee was a four.
- [x] The section's line grows a rating summary: the average and how many
      brews it came from, with no average at all until a brew has been rated.
- [x] `BrewStars` is reused as-is. It already has `onRate`, `announce` and a
      `size`, and a second star component is how two scales drift.
- [x] `sharedBrewDatabase()` is never called during render. Every call resolves
      inside the handler, per the rule in `.github/copilot-instructions.md`.
- [x] Tests: rating a recipe with no brews writes one unobserved brew, not two;
      rating a recipe brewed earlier today judges that brew instead; the summary
      reads plainly with no ratings at all.

## Task 3: The evidence suffix

Spec lines 42-62 and the acceptance bullet "evidence is absent from the stats
row while the card is in editing mode".

- [x] `library/libraryQuery.ts` selects `lastBrewedAt`, `brewCount` and
      `avgRating` as well as ordering by them. They are computed already; the
      statement simply throws them away. The three names are the contract
      `librarySort` keys on, so nothing is renamed here.
- [x] `hooks/useRecipeLibrary.ts` carries the evidence alongside the recipes.
- [x] `components/RecipeCard.tsx` draws `★4.3 · 12 · 3d` at the trailing end of
      the stats row, using the `suffix` slot `Stat` already has, and draws
      nothing at all for a recipe never brewed. Hidden in editing mode, where
      the actions take that end.
- [x] A recipe brewed but never rated shows the count and the recency with no
      star. Unrated is not zero, and a `★0` would be a verdict nobody gave.
- [x] Recency is relative and short: `3d`, `2w`, `5mo`. The formatter is shared
      with nothing that spells a date out, and it goes in
      `library/brew/brewFormat.ts` beside `formatBrewDate`.
- [x] The card's accessible label says the evidence in words. `★4.3 · 12 · 3d`
      is unreadable aloud.
- [x] Tests: the suffix is absent while editing; absent for a never-brewed
      recipe; a brewed-but-unrated recipe shows no star; the two-line budget is
      unchanged by the suffix at default and at large text sizes.

## Task 4: The shelf art

Spec §"Shelf art is a slot, not a decision". Three candidates go to testers in
one build, behind a setting, which is what the slot was built for.

- [x] `library/Settings.ts`: `shelfMarkVariant`, default `"hybrid"`. It is a
      LABS-shaped setting: it exists to find out which art wins, and it goes
      when the question is answered. It must also be added to
      `settingsSnapshot()` in `app/settings.tsx`, which is an explicit allowlist
      -- the `showHints` failure.
- [x] Variants, per the spec: **A** an accent mosaic, **B** superimposed pour
      profiles, **C** an accent field with a dot matrix glyph. Plus **hybrid**,
      the design's leading answer: C for auto shelves, B for manual.
- [x] At most three members are read, whatever the shelf holds. The rule is in
      `ShelfMark`, not in the caller, so no caller can be the one that forgets.
- [x] The grid supplies the members. `Shelf` gains accents and profiles from a
      three-row query per shelf rather than the whole membership, because a grid
      that parsed every blob in the library to draw eight squares is the lag the
      device pass already complained about once.
- [x] Every variant draws at 44 pt exactly, and the placeholder stays as the
      fallback for a shelf with no members to read.
- [x] Tests: each variant renders at 44 pt; each reads at most 3 members; the
      setting selects the variant; an empty shelf falls back.

## Task 5: Per-author shelves (#126)

- [x] `SELECT DISTINCT sharedBy` behind the same suppression gate as every other
      auto shelf, which #126 notes matters more here than anywhere: an author
      shelf is the likeliest of all of them to hold one recipe.
- [x] The Unicode fold, per `recipeIndex.ts`'s own warning on the `sharedBy`
      column: `NOCASE` is ASCII only, so grouping authors by it would file CAFÉ
      and café as two people. The `tagKey` treatment applies.
- [x] Persistence: `asStockFilters` drops ids it does not recognise, so an
      author filter would not survive a relaunch. The drop becomes deliberate
      for unknown ids only, with the author vocabulary consulted on rehydration.
- [x] The rail already speaks these ids: `filterAccessibilityLabel` reads a
      `sharedBy:` id as "Recipes that arrived from <name>", with tests. Nothing
      there changes.
- [x] Tests: two recipes from one author and three from another produce one
      shelf, not two; an author filter survives a relaunch; the fold groups
      CAFÉ with café.
